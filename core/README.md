# project-state — Python migration candidate

**Experimental local candidate; not a public or production release.** Candidate `0.1.0a49` is a Windows-only migration candidate and has not passed the complete migration or installer lifecycle gates. Use only synthetic disposable projects. Node and Python must not mutate the same project concurrently.

This is an unpublished native Python experiment, version `0.1.0a49`, separate from the public Node.js `project-state-snapshot@1.4.0-rc.15`. Contract revision 30; snapshot schema v2; general/task doctor result schema v1; list/show result schema v2. It requires Python 3.12 or later and SQLite 3.51.3 or later for explicit online database backup and restore. It has no Python runtime dependencies. Node is not used by the Python tool itself; snapshotting or comparing a Node project may probe that project's Node/npm versions.

## Implemented commands

```text
project-state --version
project-state help
project-state doctor [--task config-snapshot|config-restore --snapshot NAME] [--json]
project-state snapshot NAME [--with-seed]
project-state list [--json]
project-state show NAME [--json]
project-state compare NAME [OTHER_NAME]
project-state restore NAME --only config|git [--json] [--yes]
project-state restore NAME --only database --target DB_FILE [--json] [--yes]
project-state recover OPERATION_ID --inspect|--continue|--rollback [--yes]
project-state demo
project-state state-location show
project-state state-location check <path>
project-state state-location init <path>
```

Snapshots keep schema v2. The default Windows state root remains `%LOCALAPPDATA%\project-state-python\v1\<project-id>`. A new project with no Python state may choose one explicit same-volume root through `state-location init`; `show` and `check` are read-only. The control slot remains under the per-user state home and the selected root is revalidated on every lookup. Existing state cannot be moved or merged; pending, malformed, or conflicting registration blocks fallback. Registration uses same-volume publication for each individual volume and does not claim power-loss durability. Project identity is a hash of the normalized absolute project path; no automatic discovery or migration occurs. The Node runtime continues using project-local `.project-state`, and Node/Python must not write the same project concurrently.

The a35 state-root layout remains in effect: Windows `%LOCALAPPDATA%\project-state-python\v1\<project-id>`; Linux `${XDG_STATE_HOME:-~/.local/state}/project-state-python/v1/<project-id>`; macOS `~/Library/Application Support/project-state-python/v1/<project-id>`. The project ID is a SHA-256 of the normalized absolute project path; the raw project path is not stored in the state-root marker. Snapshots, private artifacts, lock, pins and journals are all inside that Python state root. The Node runtime continues using project-local `.project-state`; a39 does not scan, import, migrate, or choose snapshots from that directory. Cross-root snapshot reads are unsupported. Existing a33 state is not moved or deleted. Before changing runtimes, the operator must inspect any prior a33 operation with the matching a33 runtime; a39 does not detect or recover a33 journals. New Python restore journals bind a non-secret hash of the original lock owner and use an append-only resolver claim chain for each continuation or rollback. Pending a35 operations have no such owner binding, so a39 may inspect them but refuses to continue or roll them back; resolve them with the originating a35 runtime. This binding does not coordinate business-file writes with Node: never run Node and Python restore/write commands concurrently on the same project. A pre-existing a33 regular lock file may still block Node; a39 does not inspect or remove it, so follow the a33 recovery procedure and preserve ambiguous state. Config and SQLite restore require the project and private state root to resolve to the same filesystem volume; preflight rejects other layouts before creating a restore transaction. A config operation proven not to have moved its original target can be terminally cancelled through `recover --rollback`; this records that the snapshot was not applied and preserves its safety point and stage. The Python tool is not a drop-in replacement.

### State-root first initialization

New state roots are built in a unique sibling initialization container. The legacy `state-root.json` payload stays unchanged. Before the container is published, an additional `state-root.initialization.json` binds the project identity, initialization ID, parent-child directory file identity, marker file identity, and marker digest. Windows same-volume `os.rename` is used as a no-replace publication step and the published root is revalidated. A racing initializer verifies the winner rather than replacing it. If a process exits before publication, its uniquely named container is left untouched; the next attempt uses a new name. Unknown markerless official roots remain blocked and are never repaired or adopted. Older a38 readers ignore the additional proof file, while a39 validates it when present; removing that extra file makes a root indistinguishable from a legacy root and is therefore treated under the legacy marker rules. This protocol is process-crash tested on Windows, not power-loss tested.

General `doctor` is read-only. It probes Git, Node, npm, SQLite CLI and Docker availability; reports Git worktree state; compares supported direct npm lockfile versions with already-installed `node_modules`; compares only configuration filenames/key names with the newest fully validated v2 config snapshot; and warns if a legacy `files/db-original` path is present in the Python-owned state root. It does not inspect Node's project-local `.project-state`. It never runs npm, reads configuration values or opens a legacy database copy. Missing tools/baselines are `unknown`, not clean. This check does not establish restore readiness or application health.

`snapshot` supports allowlisted root config, npm dependency, runtime-pin, Git summary, and Docker Compose service-summary collection. Git collection records HEAD, attached/detached state, bounded dirty count and status sample using the guarded read-only Git preflight. A failed Git probe is skipped with a stable reason code, never reported as clean. `compare` compares validated Git metadata, exact private config bytes, dependency declarations/resolved versions/lock fingerprints, and runtime version-pin bytes. Private values, package names and versions, and digests are withheld; missing or skipped evidence is marked not compared. When comparing two validated snapshots, database capture mode, recorded schema fingerprint, table names, and recorded row counts are compared. Row contents are always explicitly marked “not compared”; matching metadata is not evidence that rows match. Live databases are not opened by `compare` and are reported as not compared. Docker service comparison remains unimplemented. Git restore preview is available for clean supported repositories; it refuses ignored-path collisions and links along target paths. Git apply remains unavailable and fails closed. Docker runs only the trusted native `docker compose ps --format json` query when a root Compose filename is present; it stores service names/states only and skips a failed query with a bounded reason code. `--with-seed` requires supported root-level SQLite files and uses Python's SQLite online backup API into private storage; SQLite engines below 3.51.3 are refused before backup work. On verified Windows, `restore NAME --only database --target DB_FILE` restores one matching root-level database only when the target and all SQLite sidecars are absent. It checks integrity, schema fingerprint and row counts. Existing targets are never overwritten, and this candidate refuses database restore on other platforms until an equivalent no-replace publication primitive is tested there. Completed restores remain pinned while rollback is available. Rollback removes the project-root target by moving the verified object into a private quarantine; it does not erase that database, and the quarantine remains for manual review. Existing snapshot names are refused.

`restore NAME --only config` previews one or more eligible config files without writing. Applying is narrower: the snapshot must resolve to exactly one `.env` or `.env.local` target. After reviewing the plan, `--yes` authorizes the apply; it creates and validates a private safety snapshot, writes an append-only journal, and checks the published file identity, size and digest. `restore NAME --only git` validates and previews a clean Git target, including commit availability, branch attachment semantics, tree modes and content-filter boundaries. Git apply remains explicitly refused, including with `--yes`; the preview changes no HEAD, refs, index or files. Git preflight also refuses dirty or unsupported repository states for config restore. Application health and automatic restart are not tested.

On Windows this candidate refuses operations when required derived paths reach the tested classic Win32 path budget (`EWINDOWS_PATH_LIMIT`). Snapshot checks its collected artifact paths before storage creation; config restore checks its target, journal, stage and safety paths before acquiring its operation lock, and the safety snapshot independently checks its collected artifacts before staging. It does not enable long paths or move a project; an operator may retry only after independently choosing a shorter isolated project path.

The printed `recover OPERATION_ID --rollback --yes` reverses a completed config restore to the pre-restore bytes (or absence). For a database restore it removes the restored path but retains the database object under the private operation quarantine. If a config displacement or SQLite publication is proven not to have happened, rollback records a distinct `cancelled` terminal state, preserves the original target (if any) and stage, and releases a SQLite pin only after validating its journal and source. This is not a snapshot restore. Targeted Windows tests exercise process termination and third-process recovery for the supported config and SQLite journal windows. New snapshots/restores are refused while a nonterminal valid operation journal exists. Malformed or foreign operation evidence is preserved and blocks new writes. This does not establish recovery for Node journals, directory-lock claims, power loss, or all interruption windows. `demo` runs snapshot, compare, preview, restore and rollback against a synthetic project in a disposable temporary directory outside the caller's current directory; it does not exercise Git or application health. Prune and hook management are not implemented and fail closed.

The Python candidate is not a full port: Git apply/recover, prune deletion and hook lifecycle are unsupported. `list`, `show`, comparison, config/database restore inputs, and read-only diagnosis accept valid managed auto/hook names. Retain Node rc.15 for Git apply, prune deletion and hooks until those features are ported. a39 retains snapshot schema v2 and the Python-only a35 state layout; no snapshot migration is performed. Node and Python journal formats remain incompatible, so an interrupted operation must be recovered by its originating runtime. Do not use this alpha candidate for important data. It does not provide general uncommitted-source recovery, existing SQLite overwrite, arbitrary file restore, automatic dependency installation, runtime switching, application restart, encryption, or general environment rollback. The local installer core still has no recoverable transaction journal, first-root recovery, activation interruption recovery, or resumable uninstall; it is not a one-click installer or a public Python package.

## Build and isolated install for migration verification

Setuptools is a build-only dependency. From an isolated build environment:

```powershell
python -m pip wheel --no-deps --no-build-isolation .
```

Install the resulting wheel only into a disposable virtual environment for local verification. No public install command is provided. The complete migration matrix and test evidence live outside the distributable package.

Business restore and recovery writes are currently enabled only on verified Windows semantics; non-Windows platforms may inspect state but mutation/recovery is refused before transaction creation. The candidate was tested on Windows with CPython 3.12.10. Python 3.12 remains in security-fix support through October 2028; use a current supported security patch. Python 3.13+, Linux and macOS are not verified for this candidate. See [CONTRACTS.md](CONTRACTS.md) for the CLI result boundary. See the [Python version status](https://devguide.python.org/versions/) and [Python 3.12.16 release](https://www.python.org/downloads/release/python-31216/).
